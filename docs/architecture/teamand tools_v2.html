Topic 01

Content / UI / Data separation.
System design level.

01 Content / UI / Data separation — can the CMS drop in later without touching components?
A
Architect
Raphy, good call raising this at system design level — not after the build. Here's how I see the three layers and exactly where the line sits between them:

Content layer — what Tanzil and Sumeet own. Lives in src/data/ and src/content/. TypeScript data files (retail.ts, sap.ts) and MDX articles. This layer knows nothing about components or CSS. Every field is typed against an interface. Wrong shape = build fails. This layer is CMS-ready from day one — the CMS API just replaces these files.

Data layer — the API routes in src/app/api/. These are the single source of truth for any consumer. The website, a mobile app, the saasinator chatbot — they all call the same routes. /api/content/[page], /api/jobs, /api/insights/[slug]. When the CMS arrives, only the data source behind these routes changes. The route interface stays identical. No consumer notices.

UI layer — components in src/components/. They accept props. They know nothing about where the data came from. A VendorCard doesn't know if its data came from retail.ts or a CMS API response. It just renders what it receives. Zero hardcoded content. Zero hardcoded colours.
Three-layer separation: Content (data files + MDX) → API routes (single interface) → UI components (props only). CMS replaces content layer only. API routes and components never change at migration.
U
UI/UX
I want to add a fourth layer the Architect didn't mention — the design layer. That's globals.css and nothing else. Not Tailwind utilities scattered in component files. Not inline styles. Not hardcoded colours anywhere in a component. The design layer is L1–L6 of globals.css and the semantic tokens in L2 specifically.

When Sumeet wants to rebrand — change the accent colour from yellow to something else — that's one value change in L2 of globals.css. Every component updates automatically. That only works if we're strict about the colour gate hook on every commit.

So the full separation is actually four layers: Content → Data API → Design tokens (globals.css) → UI components (consuming both). The components sit at the intersection of design and data but own neither.
P
Performance
One flag from me on the API routes. Edge runtime on /api/content/[page] and /api/insights — not Node.js runtime. Edge runtime has no cold start, sub-millisecond response at CDN edge. Cache headers: s-maxage=3600 for content, s-maxage=300 for jobs (ATS data, changes more frequently). This is critical — if these API routes are slow, every consumer is slow.

Also: /api/jobs should return a Last-Modified header so the browser can use conditional requests. When the ATS hasn't changed in 5 minutes, the client gets a 304 and doesn't re-render the job list.
R
Raphy
Confirmed — four layers: Content, Data API, Design tokens, UI. Edge runtime on all API routes. Colour gate enforced on every commit. That's the architecture. Architect — write this as a section in DESIGN_SYSTEM.md so the team can't accidentally violate it.
Topic 02

Taste skills + Impeccable.
Decoration or structural principle?

02 Do we add taste skills and impeccable? Where do they live in the build?
U
UI/UX — Emil Standard
Raphy, "taste" and "impeccable" aren't features you add at the end. They're discipline applied from the first component. Let me be specific about what they actually mean in code and design decisions — not abstract terms:

Taste is knowing what to leave out. The temptation on a site like this is to fill every block with content, calls to action, icons, and colour. A CIO visiting from Korn Ferry has seen everything. What stops them is restraint — a section that breathes, whitespace that signals confidence, a single amber CTA that isn't competing with five others.

Impeccable is the gap between 90% and 100%. It's the hover state that feels satisfying rather than functional. It's the Ken Burns that uses ease-in-out instead of linear. It's the amber left-border that appears at exactly 0.2s — not 0s (jumpy) and not 0.5s (slow). It's the counter that eases-out — not linear. These are 2-hour decisions that last 5 years.

Here's where they concretely live in this build:
  • Typography: H1 at –0.04em, not –0.03em. The difference is visible at 72px. Emil always went tighter.
  • Whitespace: Section padding at 100px minimum on desktop. Don't compress it to 72px to fit more above the fold. The CIO should feel arrival, not urgency.
  • Hover states: Every interactive element has a hover state. No exceptions. No bare anchor tags without transition.
  • Image treatment: Vendor logos: white monochrome at 45% opacity. Not 100% (too loud), not 30% (unreadable). 45% exactly.
  • Dark/light transitions: Where a dark section meets a light section, the transition is not a hard line — it's a 2px gradient fade. Invisible when present, jarring when absent.
C
Content Strategist
I want to add the content equivalent of taste and impeccable because it applies equally to copy.

Content taste: One idea per sentence. One primary keyword per page. One CTA per section — not three. The discipline to not say "world-class specialist experts who deliver excellence" when you can say "contractors who have run this programme." Less copy, more signal.

Content impeccable: The H1 on the homepage needs to be the best sentence on the site. Right now in home-3 it's "Enterprise tech talent, shortlisted in 72 hours." That's good. But Raphy confirmed the positioning as "contractors screened by architects, not keyword-matched." I'd push the H1 to something like:

"The contractor in that seat will make or break your go-live. We screen them like architects."

That's impeccable copy — it addresses the fear, not the feature. Raphy, I'd like to workshop the H1 with you separately before it's written into the homepage component.
S
SEO/GEO/AEO
From SEO: taste and impeccable also means not over-optimising. The worst thing we can do is have clearly keyword-stuffed copy that reads like it was written for a search engine. A CIO reads the meta description before clicking. If it reads like "SAP contractor recruitment specialist enterprise technology UAE GCC India" — they don't click.

Impeccable meta descriptions are 150 characters, benefit-led, human-written, with one location signal at the end. That's it. The keyword is there naturally. Not repeated. Not bolted on.
R
Raphy
Yes — taste and impeccable are structural, not decorative. They go into DESIGN_SYSTEM.md as a named section: "Taste and Impeccable Standards — these are not optional." Content team: workshop the H1 copy before Phase 2 starts. UI: the specific values (45% logo opacity, 0.2s hover, –0.04em tracking) go into the component spec, not left to judgment during build.
Topic 03

Dark + Light block mixing.
Rhythm, not randomness.

03 Dark + Light mixing — what's the strategy? Does it feel intentional?
U
UI/UX
Raphy, this is one of the most important decisions on the site and most teams get it wrong by treating dark/light as decoration rather than rhythm. Here's the principle:

Dark sections carry weight and authority. Hero, problem/pain, CTA, Yallo Family panel — these should be dark. The visitor should feel gravity. Dark signals: "this is serious." These are the sections where Yallo speaks with confidence about what it does and why it matters.

Light sections create trust and clarity. How it works, service pillars, case studies, partner logos — these are light. Light signals: "we're transparent about the process." A process flow on a dark background feels like a threat. On white or near-white, it feels like an honest explanation.

The alternation must be intentional and rhythmic. Dark → light → dark → light. Never two darks in a row. Never two lights in a row. The eye needs relief to reset before the next heavy message.

A
Architect
One implementation note on the light sections. The "light" tone is not pure white (#FFFFFF) everywhere. We use three light tones: pure white for process/transparency sections, canvas (#F5F4EF — warm off-white) for cards-on-surface sections, and near-white (#FAFAF8) for alternating within a light run. This prevents the eye from reading it as a single flat light expanse — there's still micro-variation within the light zones.

These three tones need to be semantic tokens in L2 of globals.css: --bg-light, --bg-canvas, --bg-near-white. Never hardcoded as hex in a section wrapper.

Topic 04

Pattern library.
What we build. What we avoid.

04 Pattern library — which patterns make this feel new? Which are traps?
U
UI/UX
I'll go through what we build, what we avoid, and why. Some of these patterns are industry traps that make a site look like every other recruitment agency — we need to be explicit about avoiding them.

Patterns we build: Ken Burns hero (already confirmed) · left-border amber on card hover · magnetic CTA button · scroll-triggered counters · horizontal role pill scroll on mobile · sticky sidebar with shared layout indicator · persona cycle on problem section · process steps with animated connector · asymmetric grid on intro sections · noise texture on dark heroes · logo monochrome at 45% opacity · bench signal (green dot + "Active bench · UK · ME · India") · split-screen vendor cards (role-dominant + small logo badge)

Patterns we avoid: Hero carousel with slide dots (outdated, not Ken Burns) · generic "Our Services" card grid with stock icons · timeline with vertical line and dots (every recruitment site has this) · accordion FAQ that looks like an FAQ (ours is minimal, inline expand) · hero with a split 50/50 image right, text left (cliché in B2B) · gradient text on every heading (reserve it for one moment per page) · box shadows everywhere (use them sparingly — only on interactive lift) · purple/blue gradients that scream "tech startup" — we are yellow/black/white only
P
Performance
Every pattern the UI team builds needs to pass a three-question performance check before it goes into the component library: 1. Does it use GPU-composited properties only? (transform, opacity — never width, height, top, left). 2. Does it respect prefers-reduced-motion? (L6 of globals.css global rule). 3. Does it have a meaningful fallback? (Ken Burns falls back to a static image, not a broken slider).

The magnetic CTA button is the one I want to flag — if it's implemented with getBoundingClientRect() on every mousemove, it will tank performance on lower-end devices. It needs to use Framer Motion's useMotionValue which is optimised for this. And it must be desktop-only — on mobile, the touch equivalent is a simple scale(0.97) on press.

Pattern library — confirmed builds

Architect-approved
Vendor Card — Role Dominant
Logo: small badge top-left (monochrome, 45% opacity). Tool name: 18px 800 weight white. Label: "Contractor roles" DM Mono amber 8px. Roles: 4–6 amber pills. Bench signal: green dot + text. CTA: "Request a contractor →". Left-border amber on hover (0.2s). Lift 4px translateY. No box-shadow.
UI/UX-designed
Persona Cycle — Problem Section
5 cards (CHRO/CIO/Head of Talent/Delivery Director/CFO). Auto-cycles 3s. Framer Motion AnimatePresence + layoutId. Active card: scale 1.02, amber border-left, full opacity. Inactive: scale 1, 40% opacity. Parallax dark background behind. Click to select manually. Stops cycling on click.
Breaking usual pattern
Horizontal Role Scroll (Mobile)
On mobile: role pills scroll horizontally with scroll-snap. Overflow-x auto, touch-action pan-x. Amber gradient fade on right edge signals more content. DM Mono 9px pills. On desktop: wrapping flex. The horizontal scroll signals depth — "more than you can see at once." No competitor does this.
Architect-approved
Sticky Sidebar — L2 Pages
position:sticky top:nav-height. height:calc(100vh - nav). All L2 functions listed for that sector. Active item: amber left-border (3px), Framer Motion shared layoutId="sidebar-indicator" slides smoothly on active change. Scrollbar: thin, amber thumb. Back link to L1 at top. Sector name as section header.
UI/UX-designed
Magnetic CTA Button
Primary amber button only. Framer useMotionValue(x,y) + useSpring({stiffness:150,damping:15}). Max ±8px displacement. On mouseleave: springs to 0. Desktop only — mobile uses scale(0.97) on press. Never on secondary CTAs. Feels premium, not gimmicky. Performance: useMotionValue, never getBoundingClientRect.
Breaking usual pattern
Dark Section Noise Texture
SVG noise pattern (fractalNoise, baseFrequency 0.65, numOctaves 3) at 3% opacity as background-image on hero and CTA sections. background-blend-mode: overlay. One CSS property, zero JS, zero performance cost. Imperceptible to most users, impossible to miss when removed. The difference between premium dark and flat dark.
Topic 05 — Flags Raised

What Raphy missed.
The team flagged these.

A
Architect — 5 flags
  • WordPress redirect strategy missing. When DNS switches from WordPress to Next.js, every old URL needs a redirect rule. The old site has URLs like /tsea-as-a-service/, /talent-in-a-box/, /managed-it-coe/ — these need 301 redirects to the new service pages or Vercel rewrites. Without this, every inbound link, every Google-indexed URL, returns 404. Critical for SEO.
  • Cookie consent not in scope. UK (GDPR), UAE (PDPL), India (DPDPA) — all require cookie consent before GA4 fires. Need a cookie consent solution (Cookiebar or equivalent, lightweight). This must be in Phase 2 before DNS switch — not an afterthought.
  • OG images not generated — they're just described. Every page needs a real 1200×630 OG image. These can be generated via next/og (Vercel Edge Image Generation) — dynamic, no manual Figma exports needed. One OG template per page type. This is in the architecture spec but not in the execution plan commits.
  • 404 and 500 pages not specced. The 404 page is the most-visited page no one designs. For a talent site, a well-designed 404 with a search bar and "Request a contractor →" CTA converts lost visitors. Add it to Phase 6.
  • Print stylesheet for case studies and white papers. A CIO who wants to share a case study will print it. If there's no print stylesheet, it prints the nav, the dark background, and looks broken. Two hours of CSS that protects the brand every time someone prints.
5 architectural gaps need adding to the execution plan before Phase 2 starts.
U
UI/UX — 4 flags
  • Skeleton loading states for jobs listing. The /api/jobs route fetches from an ATS stub. When it loads, there's a flash of empty content. Need skeleton loading cards (animated shimmer) that match the job card dimensions. One component, used on /jobs page. Without this the page feels broken on first load.
  • Image aspect ratio consistency not enforced. Sector photography needs to be consistently 16:9 for heroes and 4:5 for sector cards. If someone drops a 1:1 square image, it breaks the layout. next/image has an aspectRatio prop — we need to enforce this in the image component and document it in DESIGN_SYSTEM.md.
  • The comparison table needs updated service names. The "Yallo vs Pure Recruitment vs Pure Consulting" table on /why-yallo was designed with the old service naming. It now needs "Contract Workforce · Permanent Hiring · EOR · Managed Delivery" applied. This is a content change but also changes the table column structure.
  • Scrollbar styling missing from spec. Default browser scrollbars on the sidebar and the role pill horizontal scroll look broken on Windows Chrome. Two CSS lines: thin scrollbar, amber thumb, transparent track. Minor but the kind of thing that makes a site feel unfinished to a detail-conscious CIO.
S
SEO/GEO/AEO — 3 flags
  • No newsletter capture strategy. The architecture has a newsletter mention but no implementation plan. For GEO — capturing email addresses and delivering ME-specific market briefings (SAP talent scarcity, new programme activity in Riyadh, Dubai) builds the Yallo brand in the region over time. Need: a newsletter form, Resend list segment (UK vs ME vs India), and a monthly cadence plan. This is a Phase 3 item but needs to be in the plan now.
  • The saasinator cross-sell link — where does it go? The Yallo Family panel links to saasinator.ai but saasinator.ai is the old site. Does it link to the new saasinator.ai v2 (if live) or to a holding page? This affects OG image, canonical, and the user experience for anyone who clicks. Need Raphy to confirm the saasinator.ai status.
  • Social meta images for insight articles are not the same as page OG images. When Sumeet shares an insight article on LinkedIn, the preview image should be article-specific — not the generic site OG. next/og can generate these dynamically from the MDX frontmatter (title + author + category). Needs a dedicated article OG template. 4 hours of build time, long-term social sharing returns.
P
Performance — 2 flags
  • Hero image loading sequence not specced. Before the Ken Burns hero image loads, there's a moment where the user sees dark background and no image. This needs: a low-quality image placeholder (LQIP) generated by next/image's blurDataURL, applied to slide 1 only (priority:true). Slides 2–5 load lazily. The transition from LQIP to full image should be invisible — opacity cross-fade, not a pop.
  • Mobile hero needs a different image crop than desktop. A 1920px landscape hero image cropped for 16:9 looks great on desktop. On mobile (9:16 portrait viewport), the same image shows a tiny sliver. We need: object-position specified per slide for mobile (usually center-top on people images, center-center on landscape shots). One CSS property per slide. Missing from the hero spec.
C
Content — 2 flags
  • Sumeet's bio page is not in the architecture. The /leadership page lists the team but Sumeet's bio is the single most important trust signal on the site — Richemont, Landmark, Alshaya EMEA, Chief Architect, Gartner Peer Community. This deserves its own page or a prominently featured section. Every insight article should link to it. It's the reason a GCC CIO trusts Yallo over a generic recruiter.
  • The H1 on the homepage is not workshopped. Right now the plan says "Contractors screened by architects. Shortlisted in 72 hours." That's functional but not memorable. The best H1 on a site like this addresses the fear, not the feature. I want to workshop this with Raphy before it's locked. Request a 20-minute call.
