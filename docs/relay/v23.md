### First, correcting the premise, because it changes the question

Sumeet's instinct was that this is unmerged work. **It is not.** The repository
is fully consolidated:

| | |
|---|---|
| Branches | `main` only. Both round 14 branches deleted, local and remote |
| Worktrees | one. `../yallo-talent-website-B` removed at step 0e |
| Codebase | one tree, `main` at `99f425d`, everything merged and pushed |

There is nothing left to merge. **The two ports are not a merge artefact — they
are a consequence of how the assistant flag works**, and that is the only thing
standing between him and a single consolidated local host.

### The actual cause, in one line

`src/lib/assistant/flag.ts` reads `process.env.NEXT_PUBLIC_ASSISTANT_ENABLED`.
`NEXT_PUBLIC_` variables are **inlined by Next at build time**, so a given build
is permanently flag-on or flag-off. Showing the assistant therefore requires a
second build and, because the first one is already serving, a second port. That
is the whole of it.

### Options, for Chat to choose between

**A · Turn the flag on in `.env.local` only.** One build, one port, assistant
visible. `.env.local` is gitignored, so the committed default stays `false` and
production still ships dark — §4 forbids a committed default of `true`, not a
local override, and this is exactly the distinction it draws.
*Cost, and it is not nothing:* Sumeet's everyday local server then runs the
assistant against live credentials. Any brief sent from it writes a real
`submissions` row and sends real mail — §5's open risk 5, re-armed on the
machine he actually uses rather than on a demo port he can ignore. Also, Phase 8
would no longer be measuring the shipped configuration unless the measurement
build is kept separate and torn down.
*Effort:* one word. Instantly reversible.

**B · Make the flag runtime rather than build-time.** Read it server-side and
pass it through the tree instead of inlining it. One build then serves both
states, and the pilot can be switched on by changing an environment variable
rather than by redeploying — which is what §2.1's eventual pilot gate will want
regardless.
*Cost:* a real change to `flag.ts` and every consumer, touching the ratified
"ships dark" mechanism in the week before cutover. `check-assistant-bundle`'s
guarantee needs re-examining: today a build-time `false` lets the whole island
be tree-shaken away, whereas a runtime flag means it ships as a lazy chunk. It
would still be deferred and still absent from the initial payload, so the gate
would very likely still pass — but "very likely" is not a measurement, and that
gate exists precisely because this was worth proving once.

**C · Leave the mechanism, fix only the workflow.** One documented command that
builds `.next-r15` with the flag on and serves 3115, and a standing rule that
nothing else ever runs. One port, one build, flag stays build-time.
*Cost:* switching states means a rebuild, and any measurement run has to tear
down and rebuild afterwards.

**My recommendation, offered for Chat to accept or overrule:** **A now, B
evaluated for round 16.** A is the smallest change that delivers exactly what
was asked, it cannot affect what ships, and it is one word to undo. B is the
durable answer and the pilot switch-on will want it anyway, but it is not a
change to make days before a cutover on the strength of convenience. The live-
credentials consequence of A is the part that needs Sumeet's explicit
acceptance, not mine.
