## 4. Item 2: RBAC, live

### Migration before merge, as required

`0004_users.sql` was applied to the **live** database before the code existed in
any commit. `pnpm db:migrate` exit **0**, "Applied 1 migration(s)". Verified on

`citext` was deliberately not used: it is an extension, and an extension is a

needs nothing installed and gives the same guarantee.

### The user model as actually built

| Role | Reaches | Cannot reach |
|---|---|---|
| **admin** | briefs, conversations, case studies, articles, users | n/a |
| **editor** | case studies, articles | briefs, conversations, users |
| **ops** | briefs (read) | conversations, case studies, articles, users |

- One table decides: `src/lib/admin/roles.ts`. The nav, the route guards and
  every server action read it. `rolesFor()` has **no permissive default**, so a
  pane with no entry is closed rather than open.
- The `conversations: ["admin"]` line is the `/privacy` promise expressed in
  code, and carries a comment saying so. `/privacy` was not touched.
- `briefsWrite` is named as an admin-only capability although no brief-write path
  exists, so the first one is written against an admin-only rule rather than
  inheriting the read rule.
- **Env break-glass retained and unchanged in behaviour.** Sign-in order is table
  first, environment second. The reverse would give an address present in both
  the environment's admin role whatever the table said, so demoting or disabling
  that account in the pane would do nothing. A disabled row does **not** fall
  through to the env pair. A database error on the lookup **does** fall through,
  deliberately: an outage must be a degraded cockpit, never a lockout.
- Session JWT carries `role`. The stated cost, in the code: a role change takes
  effect at the next session issue, not instantly. Disabling is unaffected,
  because a disabled account cannot sign in again; what an existing session
  survives is a demotion.
- `/admin` no longer redirects unconditionally to briefs. An editor may not read
  briefs, so the first editor to sign in would have landed in a forbidden pane
  and been bounced out. It now lands on the first pane the role can see.

### Two layers, and why both

`requirePane()` in each pane's own server component, before it renders or
queries. `assertPane()` / `assertCapability()` at the top of every server action:
an action is a POST endpoint with a public URL, the route guard does not run on
its request, and nothing about having rendered a page earlier authorises the
action later. The nav filter is a third, cosmetic layer.

### Users pane

List, create, reset password, disable/enable. Admin only at all three layers.
The generated password is displayed once by the running app to its signed-in
admin, and exists nowhere else: not in a log, not in an email, not in a file, not
in this relay. There is no password field on the create form, by design. The last
enabled admin cannot be disabled by anyone including themselves;
`enabledAdminCount()` counts rows only and never the env identity, because the
environment is exactly what a bad deploy takes away.

**No real user row was created. The table is empty.** Confirmed at handover:
`admin-fixture-user.mjs list` → "No accounts."

## 7c. The CI fast lane, and dev.yallo.co

### The fast lane (`7fd0f7a`)

A content-only diff now runs static gates only: lint, terminology, case-study
excerpts, prose rules, published manifest, write-path invariants, taxonomy, the
redirect table's static half, and the article validation rules. Anything under
`src/`, `scripts/`, config or a workflow runs the full suite unchanged.

**Branch protection verified by API this session, not remembered:**

```
required_status_checks.contexts = ["checks"]     strict = false
```

Both lanes converge on a `checks` job that `needs` both. Two traps avoided
deliberately, and both are the failure mode the round file warned about:

- The lane is decided from the DIFF, never from a `paths:` filter. A `paths:`
  filter SKIPS the workflow, and a skipped required check never reports at all,
  so auto-merge waits for a status that is never coming.
- `checks` carries `if: always()`, because the lane that did not run is skipped
  and a skipped dependency would otherwise skip the gate too. A skipped lane is
  a pass; failed or cancelled is not; neither lane running is a failure.

The decision logic was dry-run under bash before it shipped, including the case
that matters most: `content/a.mdx` plus `src/app/page.tsx` takes the FULL lane,
and `contentious/x.ts` does too, so the `^content/` prefix does not swallow a
similarly named directory. An empty diff and a non-pull-request event both take
the full suite.

**Proven on a real run.** PR #19 (round23 into main) touches `src/`, and the run
behaved exactly as designed: `scope` passed in 11s, `content` reported
**skipping**, `full` ran. That is the lane decision working live.

**What was NOT done here, and it is the one open piece of §5.** The throwaway
content-only pull request, watched auto-merging on the fast path and reverted in
the same session, was not performed. It cannot be: a content-only PR has to be
cut from a base that already carries this workflow, and `main` does not until
#19 merges. Doing it from `round23` would have carried every source change in
the round and taken the full lane by definition, which proves nothing.
**The unblocking step is: merge #19, then open a one-line `content/**` PR and
watch it take the content lane.** The lane decision itself is already proven by
the run above; what is unproven is the auto-merge behaviour at the end of it.

**Forty seconds against nineteen minutes**, and the required context still

**Based on `round23`, not `main`, and that is not a compromise.** A
`pull_request` event runs the workflow from the head ref, so the workflow under
test is the one that ran. Basing it on `main` was not possible: `main` does not

`type-enum` on this repository is `[feat, fix, chore, data, style, perf, docs,
test, refactor, ci]`. It has no `content` type, and `publishArticle` was writing
`content(insights): ...`. Every article pull request the new pane opened would
have carried a commit message the project's own convention rejects. Fixed to
`data(insights)`, matching the case-studies path. That is precisely what §5 says
the throwaway pull request is for, and it earned its place on the first try.
