## 2. What Sumeet reported once it was live, and what each turned out to be

### The Jobs link "isn't opening the Volcanic board"

Measured while he was mid-browser-session: he was looking at a server this
session had rebuilt from the **wrong branch** — `feat/admin-otp-signin`, which
branches off `main` *before* round 27.1 or 28a and therefore carries none of
the jobs work. Not a defect in the shipped code. Rebuilt from the correct
branch, confirmed all three Jobs anchors resolve to the board with the arrow
removed, told him plainly this was this session's mistake rather than his.

### "Does `auth@yallo.co` work in Resend the way it does for CV Formatter?"

**Yes, and the reasoning generalises correctly.** Resend verifies a *domain*,
not an individual address; `auth@yallo.co` inherits `yallo.co`'s verification
the same way any other `@yallo.co` sender would, including whatever address CV
Formatter sends from. Confirmed via the Resend API with the key in
`.env.local`: `yallo.co` shows `status=verified`. Confirmed separately via
`doctl` against the live DigitalOcean app spec that `RESEND_API_KEY` exists
there as a `SECRET` value (never decrypted or displayed) and that the running
deployment is the one just merged.

**What was not proven, stated plainly rather than left implicit:** production's
`RESEND_API_KEY` was never compared byte-for-byte against the local one — it
cannot be, since App Platform reports secrets only as encrypted blobs. The
inference that production sends from the same verified `yallo.co` domain rests
on both keys almost certainly belonging to the one Resend account this
organisation operates, not on a direct comparison. Reasonable, not certain.

**No code has ever been requested, sent or verified end to end against the
real inbox path.** `signin_codes` holds zero rows as of this relay. The gates
that passed (§4) exercise the *mechanism* — hashing, expiry, the disclosure,
the callback — against fixture accounts, never a live email round trip.

## 3. PR #34 — the sign-in page, unscoped, direct from chat

No round file. Sumeet reported two things in one message: a colleague's
sign-in sent no email, and the page "looked so weird" next to a plain
email-then-code screen he'd seen elsewhere (Yallo's own CV Formatter tool).

**The missing email, diagnosed rather than assumed a defect.**
`kritika.poddar@yallo.co` has no row in `users` — confirmed by direct query,
the only account among the five closest by name is `chandrasekhar.k`.
`requestCode` did exactly what §2.3 from round 28a's own scope requires for an
unknown address: nothing, silently, indistinguishable from a disabled account
or a rate-limited one. Not fixed, because there was nothing broken to fix —
raised to Sumeet as a decision (create the account, or test with one of the
five that exist) rather than acted on unilaterally, since it names a specific
person and a role assignment is his call.

**The look, and the more consequential ask underneath it.** The page rendered
both the email step and the code step at once, unconditionally, plus a
full-size second "Owner sign-in" form with its own heading — five fields
visible before anyone had done anything. Rebuilt to show one step at a time,
decided by `sent` in the page's own query string, server-rendered, no client
state.

Sumeet also asked whether the page could simply detect which address belongs
to the owner and present a password field only for that one. **Declined, and
argued rather than silently substituted:** branching an unauthenticated
form's behaviour on the specific address typed into it is the exact class of
oracle §2.3 was written to close, pointed at the single highest-value account
rather than at membership generally. What shipped instead keeps the owner path
available to anyone — a native `<details>`/`<summary>` disclosure, this
codebase's own established pattern (`payloadDisclosure` on the briefs pane) —
closed by default, reopening itself server-side on its own failure, so the
primary flow is the only thing competing for attention without the second
door depending on JavaScript or being genuinely hidden.

`scripts/lib/admin-sign-in.mjs` now opens that disclosure before filling the
owner form. Recorded as adapting the helper to a real UI change rather than
weakening it: it still drives the actual control through actual UI, one click
earlier, and is a no-op on any page carrying no `<details>`.

Smaller items in the same pass: the "keep me signed in" checkbox lost its
mono/uppercase treatment (a field name's register, not a sentence's); the code
input took the mono/tabular/letter-spaced treatment DESIGN.md's Three Jobs
Rule gives a reference number; the flower mark sits beside the `<h1>` as a
sibling rather than inside it, so it cannot join the heading's accessible name
the way the site header's own mark once did (round 10, WCAG 2.5.3); `.submit`
gained hover, focus, active and disabled states it lacked cockpit-wide, fixed
on the shared class rather than only where it was noticed.

**A defect this session caused and caught before it shipped.** The new
step-two copy read "...used once — enter it below", an em dash, which
`check-terminology.mjs` bans in published copy. It surfaced first as an
unrelated Playwright test failing —
`e2e/terminology-stripper.spec.ts`'s comment-stripper self-test — because that
gate scans the whole `src/` tree rather than only its own fixture, so a real
violation anywhere failed the fixture's exit-code assertion. Reproduced
directly outside Playwright to find the actual cause rather than accepting
"flaky test" as an answer; the reproduction named the exact line. Fixed at the
copy, not the test, and the full 158-test suite went green on the next run.
