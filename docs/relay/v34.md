## 7. What the database now serves, and what it does not

**Serving from the database:** `/case-studies` and every study, `/insights` and
every article, the three taxonomy archives, the homepage rail, the platform
module evidence sections, the assistant corpus, `sitemap.xml` and `llms.txt`.
The sitemap and `llms.txt` are dynamic and change on publish.

**Not prerendered at build, deliberately.** Canon A2 removed the build from the
publishing path, so a route that exists only because a build enumerated it is a
route a new article would not have until the next deploy. `generateStaticParams`
returns nothing for the content routes; they generate on first request, cache,
and the publish action's revalidation refreshes them. It also means a build needs
no connection string, which is what lets CI build this repository at all.

**Publishing revalidates wider than the piece:** its own route, the index, every
taxonomy archive it is tagged with, `sitemap.xml`, `llms.txt`, and the homepage
for a case study. `updateTag` rather than `revalidateTag`, because Next 16 splits
them and only the former gives read-your-own-writes inside a Server Action. A
publisher shown the old page has been told their publish did not work.

**Ordering is a column and one transaction.** The staged-order cookie, its banner
and its pull-request path are removed, not dormant. The pane moves a study up or
down and the whole sequence is rewritten, which is what a drag-and-drop surface
will send.

## 8d. Item 3, the four roles, and why it did not wait for 25b

**It closes a defect item 1 opened.** The ratified `/privacy` wording shipped in
item 1 and describes a small, named group of administrators reading assistant
conversations. Until item 3, the code had three roles and `admin` could not reach
conversations at all, so the notice was **wider than the code**. A notice wider
than the code is the same defect as one narrower than it, in the other direction,
and it is not a state to hand over.

| Role | Reaches |
|---|---|
| `owner` | everything, and cannot be disabled, demoted or reset by anyone |
| `admin` | everything: briefs, conversations, case studies, articles, accounts |
| `editor` | articles and case studies |
| `ops` | briefs |

**The environment break-glass maps to `owner`**, not to `admin`. Break-glass is
for the failure nobody chose, and an owner is the only role that can restore
another owner; a break-glass session that could not do that would arrive with
exactly the wrong power in exactly the situation it exists for.

**`canManageAccount` is separate from `canDo('usersManage')` on purpose.**
Managing accounts and managing THIS account are different questions, and folding
the second into the first is how a target-blind capability check grants more than
it means. It gates disabling, demoting **and** resetting a password, because
seizing an account is the same act as disabling it.

**Red-proven: `e2e/roles.spec.ts`, 49 tests, exit 0.** Every cell of the access
matrix is asserted in **both** directions, because a role table asserts a
negative and a negative nobody has watched holding is a table nobody has reason
to believe. The matrix is written out rather than derived from the code it
checks: a test that computes its expectation from the thing under test asserts
only that the code agrees with itself.

Watched failing twice, then restored:

| Loosening | Result |
|---|---|
| `editor` added to `conversations` | **1**, red on the matrix cell AND on the `/privacy` assertion |
| `canManageAccount` returning true unconditionally | **1**, red on every owner case |
| Both reverted | **0**, 49 passed |

**No account was created.** Every case is a pure function over a role string.
